This statement is correct. Through the use of the REMOTE_LISTENER initialization parameter, a database instance can register its services with listeners residing on different hosts. F. Service names can be statically defined for a listener.

This statement is correct. While dynamic registration (using PMON and LOCAL_LISTENER/REMOTE_LISTENER parameters) is the preferred and default method for active services, service names can also be statically defined in the listener.ora file. This is often necessary for:

Databases that are not automatically registering (e.g., older versions, or specific configurations).
When a database instance is not running and you want the listener to still report its existence (though it won‘t be connectable).
For specific administrative connections where dynamic registration might not yet be complete.

External Naming: Using NIS or other third-party naming services.

      sql
      SELECT last_name, department_id

    Correct:

    A. If it is set to true at the instance level, then no sessions can have immediate segment creation.
    This statement is correct. The DEFERRED_SEGMENT_CREATION initialization parameter (which can be set at the system/instance level) controls the default behavior. If it‘s set to TRUE at the instance level, then new tables (and their associated LOB segments) will generally defer segment creation until the first row is inserted. While you can override this for specific tables using SEGMENT CREATION IMMEDIATE in the CREATE TABLE statement, the default behavior for all sessions will be deferred. The phrasing “no sessions can have immediate segment creation“ is slightly ambiguous, but it refers to the default behavior for new objects created within those sessions, implying that explicit overrides are still possible for individual objects, not that the ability to create immediate segments is completely removed. However, if the question implies a universal default without exceptions, then yes, the default for new objects in all sessions would be deferred.

    E. It is the default behavior for tables.
    This statement is correct. Starting with Oracle Database 11g Release 2, DEFERRED_SEGMENT_CREATION is set to TRUE by default. This means that when you create a new table, Oracle creates the table object in the data dictionary but does not allocate any disk space (segment) for it until the first row of data is inserted. This saves space, especially for applications that create many tables that might remain empty for a long time.

    Incorrect:

    B. It is the default behavior for indexes.

    Explanation for “A migrated row can also be chained.“ (This is implicitly correct based on the understanding of both concepts)

    Row Migration: Occurs when an UPDATE operation increases the size of a row such that it no longer fits in its original block. Oracle moves the entire row to a new block, leaving a pointer (forwarding address) in the old block.
    Row Chaining: Occurs when a row is too large to fit into a single data block, either at the time of INSERT or subsequent UPDATE. The row is then stored in multiple row pieces, which are “chained“ together across different blocks.
    Why it‘s true: A row might initially fit in a block but then be updated and migrate to a new block. If, at the same time, the updated row becomes so large that it still cannot fit entirely within that new block, it can then become chained across multiple blocks, even in its migrated state.     Oracle 19c Concepts: “Oracle Database can only store 255 columns in a row piece. Thus, if you insert a row into a table that has 1000 columns, then the database creates 4 row pieces, typically chained over multiple blocks.“
